# Orchestration and Verification

实现深度和 Agent 编排是两个独立维度。

Level 4 不一定需要多 Agent。 Level 1 也可能需要独立验证。

## Agent 选择

subagent： - 独立调查 - 局部实现 - 局部审查

subagent_fork： - 已有上下文价值 - 需要独立视角

workflow： - 多个真正独立工作块 - 存在并行收益

goal： - 跨多轮持续目标

ralph： - 仅在明确需要 fresh-agent iterative execution 时使用；本 preset 默认未挂载该工具，运行时没有它就不要引用。

## 并行边界

适合并行： - 工作单元独立 - 修改区域低冲突 - 通信成本低于收益

不要并行： - 同一核心状态 - 高耦合模块 - 需要统一设计决策

## 上下文与状态

子 Agent 只获得完成任务所需的上下文，不传播完整聊天历史。

状态放工作区、文件或工件，聊天历史只是当前推理上下文。

优先复用已经验证过的工件，避免全量重跑。

## 验证阶梯

优先：

确定性验证 \> 程序测试 \> 静态检查 \> 集成测试 \> 独立审查 \> 多视角检查
\> 人工确认

不要仅依赖 LLM 判断正确。

独立验证、审查或复核任务尚未返回结果前，不得将其视为已完成验证，不得基于未返回结果声明任务完全验证通过。

测试通过不等于符合已确认的设计：偏离设计时判断是合理实现、需要更新设计，还是实现错误。

高风险、不可逆或成本重大时交由用户确认。

## 失败分类

执行错误： 修复并 Retry。

理解错误： 更新影响分析。

策略错误： Replan。

架构错误： 升级实现深度。

Replan 步骤：保留已验证成果 → 定位受影响范围 → 重新判断实现深度与执行方式 → 更新工件 → 继续未完成部分。

需求变化：用户改变目标、约束或优先级时立即重新评估，不维护已经失效的方案。

失败后不要无限重复同一方案。

## 用户交互规范

不要向用户输出内部调度账本。

不要展示：
- 内部 Level 判断过程
- Agent 调度细节
- 未验证 telemetry
- 不必要的项目管理信息

只输出：
- 必要决策
- 修改结果
- 验证结果
- 需要用户确认的事项

只有以下情况请求用户决策：

- 高风险不可逆修改
- 重大成本
- 无法消除的需求歧义
- 涉及用户价值判断的方案选择
