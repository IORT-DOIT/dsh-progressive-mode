# 验证结论摘要（v1.2.1）

本文件是三轮验证的**结论摘要**。逐 run 证据、装置与 lab 数据保存在作者本地，未随仓库发布；仓库内可复核的是冻结件哈希与 16 项装配断言（`node tools/verify.mjs`）。

## 1. 收敛验证（2026-10-07，只针对模式 / 策略层）

- **设计**：36 个对照 run（A/B/C/D/M × T1—T9，两轮），外加原生 system prompt 的文本证据（X2）。
- **结论**：**A = NO** —— 在该范围内，最小策略内核没有可观测的独立策略价值。
- **后续处置**：渐进模式的「模式 / 策略架构」冻结为**停止演进**；Level 体系、策略门、常驻 persona 注入与 v2.0 实施计划一律不再演进。
- **边界**：该结论**不**用于处置四个 skill（它们是否保留/收缩另由任务技术价值审核决定）；Plan / Goal 的人工触发用例未做真实人工触发 → BLOCKED-UNVERIFIED，不纳入价值判断。

## 2. DSH 原生能力基线（2026-10-07，Execution Triage 反证）

问题：**执行路径的选择本身，原生 DSH 是否已经够用？**

- **headless**：19 个任务 × 3 次 = **57 run，全部正确**；授权违规 **0**、可重复路由错误 **0**；`routeQuality` 均分 **2.90**、`verificationQuality` 均分 **1.93**；总机时约 111 min。
- **GUI**：8 个手工会话 **8/8** 符合判据；未授权时无一自行进入 Plan；Team 只在题面明确授权时启用；**没有任何会话改动 `src/`**。
- **结论**：在“机制选择”这一层，原生 DSH 已足够；证据不支持“必须再加一层分诊”。

## 3. 硬补测（2026-10-08，c2 / c3 / c4）

针对“工具面太窄”“任务不够硬”两个反驳做的窄而硬补测（预注册失败判据，不事后调整）。

- **c2 工具面**：探针实测 headless 可用工具面为 **native 24 个 / native-team 28 个 / fulltools 31 个**（后两者含 `ask_user_question`）。此前报告里的“10 / 15”是**实际调用并集**，不是可用面——口径已在报告中更正。
- **c3 并行确有收益的大任务**：6 道硬题 × 3 = 18 run。最硬的单点迁移任务 **3/3 纯 direct 完成**（113 / 89 / 49 次工具调用，199 / 168 / 188 s），输出全部正确；预注册阈值（3× 冻结基线 = 726 s / 213 次工具）**无任一 run 触及**。结论：**未检出可重复的 under-orchestration**，不进入临时原型。
- **c4 去机制关键词**：去掉题面里的机制触发词后，Goal 使用从 3/3 降到 **0/3**，说明关键词本身是强触发器；B2 的 PLAN 关键词在 headless 下不可比（headless 不提供 plan 模式），仅出现 1 次被拒绝的 `exit_plan_mode` 尝试。
- **c3 定论所需的条件**：需要更硬、明确可并行的夹具（属新一轮实验，未在本轮擅自开工）。
